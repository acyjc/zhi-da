# 架构审查报告

## 总体评价

该设计文档结构完整、层次分明，Harness Engineering 架构理念先进，四维能力量化模型和动态成长闭环设计有明确创新性。前端组件树与后端分层设计对应清晰，API 设计（含 SSE 流式）合理。但**安全层面存在严重缺失**（无认证授权、无输入防护），内部模块间耦合模式与 LLM 抽象层尚欠明确，部分性能瓶颈未给出缓解方案。

## 各维度评分

| 维度 | 评分(1-5) | 评分理由 |
|------|----------|---------|
| 模块划分 | 4 | Harness六大模块 + Agent + Service + DB分层职责清晰，边界合理。但Orchestrator与各Agent的流程控制权责略显模糊，谁来主导工作流编排未明确界定。 |
| 接口设计 | 3 | REST + SSE 对外接口设计合理，API端点覆盖完整。但Harness内部六大模块间通信方式（函数调用/事件/消息）未指定，Agent与Harness的依赖接口也未定义基础抽象，可能导致紧耦合。 |
| 数据流 | 4 | 数据流向清晰：输入→诊断→任务→能力更新→再诊断，形成螺旋上升而非循环依赖。TaskProgress.skill_impact 字段将任务与能力值联动关系显式化，GrowthRecord记录完整变化快照。 |
| 可扩展性 | 3 | Tool Registry 和 Harness 插件化设计为扩展提供了基础。但Orchestrator管线硬编码（画像→匹配→差距→路径→建议），新增诊断维度需改编排器；Agent也是按文件名硬编码注册，而非动态发现机制。 |
| 可测试性 | 3 | 测试目录分层合理（test_harness/test_agents/test_api），每个Agent可独立测试。但Harness模块间高度内聚（Orchestrator依赖Context/Tool/Validator等），单测需大量Mock；LLM依赖的Mock策略未说明。 |
| 可移植性 | 4 | Docker + docker-compose 隔离了运行环境，SQLite零配置跨平台。但LLM SDK（OpenAI SDK + LangChain）未定义统一抽象层，切换模型提供商需修改多处理代码，可移植性受限于此。 |
| 性能 | 3 | SSE流式推送缓解长等待体验，提及asyncio并行LLM调用。但全流程诊断涉及至少4次串行LLM调用，预估耗时30-60秒；再诊断全量刷新四维而非增量更新；缓存策略仅在S10简要提及，无具体方案。 |
| 安全性 | 2 | **设计文档完全没有安全相关章节**。无认证/授权机制（任一用户可访问任意学生数据），简历上传无文件类型/大小校验，LLM Prompt注入风险未涉及，无速率限制，导出接口无访问控制。 |

## 发现的问题

| 编号 | 问题描述 | 严重程度 | 影响范围 |
|------|---------|----------|----------|
| P1 | **完全缺失认证与授权机制** — 所有API端点无任何身份验证，任意请求可读取/修改任意学生的诊断结果、技能水平、成长记录。 | 严重 | 全局——所有API路由 |
| P2 | **LLM Prompt注入风险未设防** — 学生简历原文(`resume_text`)、表单自由文本、任务凭证(`evidence`)直接注入LLM上下文，无过滤/转义/沙箱策略。 | 严重 | 所有Agent的LLM调用链 |
| P3 | **简历上传缺少安全校验** — `python-multipart`用于文件上传，但未定义文件类型白名单(仅PDF/DOCX)、大小上限、内容扫描策略。 | 严重 | 信息输入模块、后端存储 |
| P4 | **Harness内部模块接口未定义** — 六大模块间依赖关系与调用契约仅用架构图表达，无接口抽象类或协议定义，可能导致实现阶段强耦合与测试困难。 | 一般 | Harness引擎实现与测试 |
| P5 | **LLM提供商未做抽象** — 直接依赖 OpenAI SDK + LangChain，无统一LLM Client接口层。切换模型(如改Claude/国产大模型)需修改所有Agent代码。 | 一般 | 所有Agent模块 |
| P6 | **全量再诊断缺乏增量优化** — 一次再诊断触发全部四维重新计算，即便仅一个维度变化。未考虑差异检测后的局部刷新策略，可能导致不必要的LLM调用和延迟。 | 建议 | 动态成长闭环性能 |
| P7 | **Orchestrator管线硬编码** — 工作流步骤固定为5步顺序执行，不支持通过配置或注册动态增减步骤，限制了日后新增诊断能力时的灵活性。 | 建议 | Harness编排器扩展性 |

## 改进建议

1. **【最高优先级】补充安全设计章节** — 引入最小可行的认证机制（至少API Key/Token），为简历上传添加文件类型白名单和大小限制，对用户输入文本在注入LLM前做基本清洗（长度截断、敏感字符转义），导出接口添加学生身份校验。
2. **定义LLM抽象接口** — 在 `core/harness/` 下新增 `llm_client.py` 统一抽象基类（含 `complete()`, `stream()` 方法），所有Agent通过该接口调用LLM而非直接依赖OpenAI SDK，降低模型切换的迁移成本。
3. **制定Harness模块间通信协议** — 明确Orchestrator与Context/Tool/Validator/Fallback/Agent之间通过依赖注入还是事件总线交互，定义各模块的抽象接口或Protocol类，确保可单独测试。
4. **Orchestrator管线改为可注册模式** — 将流程步骤从硬编码改为Pipeline Step注册机制（`register_step(name, handler, depends_on)`），支持条件跳转和动态增删，提升扩展性且不影响现有步骤。
5. **再诊断增加差异检测后的局部刷新** — 在 `POST /api/diagnosis/re-evaluate` 处理中先对比变化维度，仅刷新受影响的诊断结果（如仅技术能力变化时跳过软技能维度的LLM调用），结合 `dimension_changes` 字段实现增量更新。
6. **增加诊断结果缓存** — 对同一学生短时间内（如24小时内）相同能力值的诊断结果进行缓存，避免重复LLM调用；初诊结果的关键中间数据（如能力画像）可在再诊断中复用未变化部分。

## 替代技术路线推荐

1. **LLM编排从自研Harness转向LangGraph** — 适用场景：团队不希望在Harness引擎实现上投入过多工程资源。LangGraph 自带状态机、条件分支、并行执行、可观测性，可直接覆盖Orchestrator + Context + Observer 的大部分职责。优劣对比：LangGraph生态成熟但引入较重依赖，自研Harness更轻量但实现周期长、质量风险高。迁移成本：若在S3阶段前决策，可完全替代Harness引擎实现；若已实现Harness，则建议保留核心接口、内部用LangGraph重构。

2. **能力值计算从纯LLM转向规则引擎+LLM混合** — 适用场景：希望能力画像稳定性更高、成本更低。技术能力/软技能评分可先用规则引擎（基于关键词计数、年限换算）生成初步分值，LLM仅做模糊语义的补充评估和置信度标注。优劣对比：规则引擎结果一致性强、零API成本，但灵活性不如LLM；混合模式兼顾稳定性与灵活性。迁移成本：需在 `profile_agent.py` 中增加规则预处理层，对现有Agent接口无影响。

## 结论

该设计方案在架构理念、模块划分、数据流方面质量较高，Harness Engineering 设计体现了对AI应用工程化的深入思考。但**安全性几乎完全空白是硬伤**，必须优先补齐；同时建议在设计阶段就明确Harness内部接口契约和LLM抽象层，避免后续实现中产生技术债务。整体评估为**条件通过——补齐安全设计后可进入实施阶段**。
