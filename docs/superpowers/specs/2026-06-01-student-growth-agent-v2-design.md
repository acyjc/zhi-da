# 职达学生成长智能体 V2 产品设计方案

> 日期：2026-06-01  
> 产品方向：学生成长诊断与路径规划  
> 核心定位：以学生为第一用户的职业成长决策助手  
> 协同原则：企业提供真实岗位和招聘反馈，学校承担轻量治理，智能体负责匹配、解释和动态规划

详细施工拆分、组件复用边界和阶段验收标准见：

> [`2026-06-01-zhida-v2-implementation-plan.md`](./2026-06-01-zhida-v2-implementation-plan.md)

## 一、产品结论

职达不应继续扩展为大型教务系统或招聘管理系统。产品的核心任务是帮助学生持续回答五个问题：

1. 我适合什么职业方向？
2. 我与目标岗位之间差在哪里？
3. 在有限时间内，我下一步最应该做什么？
4. 我完成任务后，是否真的更接近目标？
5. 当前有哪些值得投入时间争取的机会？

产品主线从“生成一份诊断报告”调整为：

```text
建立学生档案
    ↓
智能体识别信息缺口并主动追问
    ↓
结合真实岗位完成能力诊断和机会匹配
    ↓
学生选择主目标与备选目标
    ↓
生成一周可执行任务
    ↓
学生提交成长证据
    ↓
智能体重新判断并动态调整计划
    ↓
学生自主授权投递
    ↓
企业反馈回流，继续优化进阶路径
```

学校不参与人才推荐决策。学校提供可信环境、基础管理和异常处理能力。

产品品牌表达统一为：

> 职达：看清方向，补齐能力，抵达理想职业。

## 二、设计原则

### 2.1 学生优先

学生端是核心产品。企业端和学校端服务于学生成长闭环，而不是形成三个等重量的平台。

### 2.2 决策优先于报告

图表、雷达图和历史记录用于解释结果，但首页必须优先告诉学生“现在应该做什么”。

### 2.3 证据优先于自评

能力分数必须关联证据和置信度。简历自述、项目仓库、课程成绩、任务提交和企业反馈的可信度不同，不能等价处理。

### 2.4 自动匹配，学生自主授权

岗位匹配由系统自动完成。学校不需要人工筛选或逐个推荐。学生决定是否授权投递，企业只能查看已授权资料。

### 2.5 规则计算与 LLM 协同

规则算法负责稳定、可复现的计算；LLM 负责语义理解、主动追问、个性化解释和动态规划。不能让 LLM 凭空决定所有分数。

### 2.6 渐进式交付

只建设真实用户近期会使用的能力。复杂课程诊断、培养方案迭代和大型教务管理能力后置。

### 2.7 品牌命名一致性

学生端避免使用“工作台”“管理”“任务中心”等后台语言。用户可见命名围绕“方向、进阶、抵达”展开：

| 通用功能描述 | 学生端品牌命名 | 表达重点 |
|--------------|----------------|----------|
| 学生首页 | 职达首页 | 当前目标和下一步行动 |
| 职业探索 | 方向探索 | 找到适合自己的职业方向 |
| 能力档案 | 能力画像 | 看清现状、证据和差距 |
| 成长计划 | 进阶路径 | 从当前位置走向目标岗位 |
| 就业机会 | 职达机会 | 发现值得投入时间争取的岗位 |
| 诊断记录 | 成长轨迹 | 理解每次变化及其原因 |
| AI 顾问 | 职达顾问 | 获得带个人上下文的建议 |
| 本周行动 | 本周进阶 | 聚焦当前最值得完成的事项 |
| 智能体提醒 | 职达建议 | 在关键节点主动提示下一步 |
| 能力短板 | 待补能力 | 明确优先补齐的能力 |

技术层继续使用稳定、清晰的领域术语，例如 `workspace`、`profile`、`plan` 和 `opportunities`。品牌命名仅作用于用户可见界面和产品文案。

## 三、角色与边界

| 角色 | 核心目标 | 主要操作 | 明确不承担 |
|------|----------|----------|------------|
| 学生 | 明确方向、完成成长任务、获得合适机会 | 上传资料、回答追问、选择目标、提交证据、自主投递 | 手工维护复杂档案、理解复杂算法 |
| 企业 | 发布真实岗位、获取已授权候选人、反馈招聘结果 | 维护岗位、查看授权资料、回填面试和录用结果 | 查看未授权学生资料、修改学生能力分 |
| 学校 | 维护可信环境、管理学生状态、处理异常 | 学生管理、企业审核、岗位审核、反馈留痕、运营统计 | 人工推荐人才、替学生授权、修改匹配结果、建设复杂教务流程 |
| 智能体 | 降低学生决策成本 | 追问、诊断、匹配、解释、规划、调整、提醒 | 伪造证据、替学生做最终投递决定 |

## 五、学生端详细设计

### 5.1 职达首页

职达首页是学生登录后的默认首页，不再以多个并列诊断 Tab 作为首屏。页面需要持续回答一个核心问题：距离目标职业更近一步，现在最值得做什么？

首屏信息按行动优先级排列：

| 区域 | 内容 | 目的 |
|------|------|------|
| 当前目标 | 主目标岗位、备选岗位、当前匹配度、最近变化 | 让学生知道当前方向 |
| 本周进阶 | 1–3 个优先任务、预计耗时、完成标准 | 降低执行门槛 |
| 职达建议 | 信息缺口、计划调整、适合岗位、企业反馈 | 主动介入关键节点 |
| 待补能力 | 当前最值得补齐的 3 项能力 | 避免信息过载 |
| 机会入口 | 立即可投递、短期可争取的岗位数量 | 连接成长和求职 |
| 最近进展 | 新增证据、匹配度变化、已完成任务 | 形成反馈感 |

### 5.2 方向探索

当学生没有明确目标岗位时，不强迫其直接填写目标。

智能体收集：

- 专业、年级和毕业时间
- 已有技能和项目经历
- 兴趣方向
- 偏好城市
- 薪资期望
- 工作方式偏好
- 每周可投入时间

系统给出 3 个候选方向：

| 字段 | 说明 |
|------|------|
| 方向名称 | 例如 Python 后端开发 |
| 当前适配度 | 规则计算后的基础值 |
| 推荐理由 | LLM 解释已有优势和可迁移能力 |
| 关键短板 | 最影响入门的 1–3 项能力 |
| 预计补齐周期 | 基于时间预算估算 |
| 岗位机会数 | 当前系统中可用岗位数量 |
| 决策 | 设为主目标、设为备选、暂不考虑 |

学生可以保留一个主目标和最多两个备选目标。

### 5.3 能力画像

能力画像沿用四维结构，但每个能力项增加证据和置信度。

```text
技术能力
├── Python：72 分，置信度高
│   ├── 简历提及 2 个项目
│   ├── 已提交课程项目仓库
│   └── 完成后端 API 实践任务
├── SQL：58 分，置信度中
│   ├── 简历提及数据库使用
│   └── 缺少可核验项目证据
└── Docker：35 分，置信度低
    └── 尚未提交相关证据
```

证据来源：

- 简历解析
- 学生补充回答
- 项目链接或作品
- 课程和证书
- 成长任务提交
- 自测或模拟面试
- 企业招聘反馈

评分展示必须同时回答：

```text
为什么得到这个分数？
当前判断是否可信？
补充什么资料可以提高判断准确度？
```

### 5.4 进阶路径

长期路径只保留方向性阶段目标。学生日常使用的是滚动生成的一周任务。

任务卡片字段：

| 字段 | 说明 |
|------|------|
| 任务名称 | 使用动词开头，例如“为项目补充 Docker 部署” |
| 解决差距 | 关联具体岗位和能力缺口 |
| 预计耗时 | 30 分钟至 3 小时 |
| 操作步骤 | 控制在 3–5 步 |
| 推荐资源 | 课程、文章、实验或示例项目 |
| 提交证据 | 仓库链接、截图、文档、测试结果或文字说明 |
| 完成标准 | 可核验条件 |
| 预期影响 | 预计改善的能力项和影响区间 |

智能体根据学生每周可投入时间控制任务数量。默认只给出 1–3 个任务。

### 5.5 职达机会

岗位不再使用“学校推荐”叙事。系统自动匹配后，按行动建议分组：

```text
职达机会
├── 立即可投递
├── 短期可争取
└── 长期成长方向
```

岗位卡片字段：

| 字段 | 说明 |
|------|------|
| 岗位信息 | 企业、岗位、城市、薪资区间 |
| 匹配度 | 规则算法基础分和 LLM 综合建议 |
| 分类 | 立即投递、短期可争取、长期方向 |
| 推荐理由 | 已满足条件、可迁移能力和优势证据 |
| 关键短板 | 当前尚未满足的要求 |
| 补齐周期 | 基于时间预算估算 |
| 状态 | 未处理、已授权、面试中、已录用、企业拒绝 |
| 操作 | 查看依据、授权投递、暂不考虑 |

### 5.6 职达顾问

职达顾问不是通用聊天入口，而是带学生上下文的职业成长助手。

可回答的问题：

- 为什么我的后端岗位匹配度只有 68%？
- 我每周只有 6 小时，应该优先做什么？
- 我适合转数据分析方向吗？
- 完成 Docker 项目后，哪些岗位会更适合我？
- 企业拒绝了我的申请，下一步应该调整什么？

职达顾问可读取：

- 当前能力画像
- 证据记录
- 主目标和备选目标
- 最新诊断结果
- 当前任务和完成情况
- 已授权岗位
- 企业反馈

职达顾问不得读取或暴露其他学生信息。

## 六、智能体工作机制

### 6.1 智能体不是固定报告生成器

当前固定流程：

```text
画像 → 匹配 → 差距 → 路径 → 建议
```

调整为带条件判断的工作流：

```text
读取学生资料
    ↓
判断信息是否足够
    ├── 否：生成追问，等待学生补充
    └── 是：进入诊断
            ↓
        调用岗位查询和匹配工具
            ↓
        生成目标建议和差距解释
            ↓
        根据时间预算生成本周任务
            ↓
        等待证据提交或企业反馈
            ↓
        判断是否需要局部更新或重新规划
```

### 6.2 工具职责

| 工具 | 输入 | 输出 | 使用场景 |
|------|------|------|----------|
| `get_student_profile` | `student_id` | 学生基础档案 | 获取上下文 |
| `get_student_evidence` | `student_id` | 能力证据列表 | 判断置信度 |
| `search_jobs` | 方向、城市、关键词 | 候选岗位 | 方向探索 |
| `get_job_requirements` | `job_id` | 岗位能力模型 | 差距计算 |
| `calculate_match` | 学生画像、岗位模型 | 可复现匹配分和差距 | 核心计算 |
| `search_resources` | 能力缺口 | 课程和资源 | 生成任务 |
| `get_growth_history` | `student_id` | 历史诊断和任务证据 | 动态调整 |
| `get_application_feedback` | `student_id` | 企业反馈 | 优化进阶路径 |

### 6.3 匹配算法边界

基础匹配分由规则算法计算：

```text
基础匹配分 =
    技术能力匹配 × 岗位权重
  + 项目经验匹配 × 岗位权重
  + 软技能匹配 × 岗位权重
  + 领域知识匹配 × 岗位权重
```

LLM 在基础结果之上负责：

- 理解项目经历与 JD 的语义相关性
- 识别可迁移能力
- 结合偏好和时间预算进行排序
- 解释推荐原因
- 判断是立即投递、短期可争取还是长期方向

最终页面必须同时保留基础计算依据和 LLM 解释，避免不可复核的“神秘分数”。

### 6.4 主动介入规则

智能体应在以下节点主动出现：

| 触发条件 | 智能体行为 |
|----------|------------|
| 简历信息不足 | 提出 2–4 个关键追问 |
| 目标岗位差距过大 | 推荐备选路径并解释转换成本 |
| 一周内未完成任务 | 缩减计划或调整任务粒度 |
| 新证据提交 | 局部刷新能力评分和匹配结果 |
| 新岗位匹配度较高 | 通知学生查看机会 |
| 企业反馈拒绝 | 将原因转换为下一阶段行动 |
| 企业录用 | 记录结果并沉淀成功路径 |

## 七、学校管理后台

### 7.1 定位

学校端是轻量治理后台，不是人工推荐中心，也不是教务管理平台。

核心能力：

```text
学生状态管理 + 企业岗位治理 + 反馈留痕 + 基础统计
```

### 7.2 工作台

只展示需要管理员行动的指标：

- 待审核企业
- 待审核岗位
- 资料不完整学生
- 长期未活跃学生
- 待补充企业反馈
- 高频能力缺口

### 7.3 学生管理

学生列表字段：

| 字段 | 用途 |
|------|------|
| 姓名、专业、年级 | 基础识别 |
| 主目标岗位 | 判断发展方向 |
| 诊断状态 | 未诊断、待补充、已完成 |
| 最近诊断时间 | 判断数据是否过期 |
| 最高匹配岗位和分数 | 快速了解状态 |
| 投递状态 | 未投递、已授权、面试中、已录用 |
| 最近活跃时间 | 识别需要提醒的学生 |
| 操作 | 查看详情、发送提醒、标记异常 |

筛选项：

- 专业
- 年级
- 目标岗位
- 诊断状态
- 投递状态
- 最近活跃时间

学生详情允许学校查看：

- 基础信息
- 脱敏能力画像摘要
- 诊断版本历史
- 成长任务进度摘要
- 已授权投递记录
- 企业反馈
- 系统异常标记

学校默认不可查看：

- 未授权的完整简历
- 学生与职达顾问的私人对话
- 学生浏览过但未授权的岗位
- 与运营无关的个人隐私信息

### 7.4 企业与岗位

学校执行：

- 企业信息审核
- 岗位合规审核
- 岗位下线
- 异常岗位标记

学校不执行：

- 人才人工筛选
- 学生人工推荐
- 匹配结果修改

### 7.5 反馈记录

按时间线查看：

```text
系统匹配 → 学生授权 / 暂不考虑 → 企业查看 → 面试 → 录用 / 拒绝
```

反馈记录用于异常定位和运营统计，不要求学校介入每条流程。

## 八、企业端

### 8.1 岗位管理

企业维护：

- 岗位名称
- JD 描述
- 城市和薪资区间
- 能力要求
- 四维权重
- 岗位状态

系统可以使用 LLM 从 JD 中提取结构化岗位模型，企业确认后发布。

### 8.2 授权候选人

企业只能看到学生主动授权的候选人。

候选人详情包括：

- 基础信息
- 脱敏简历
- 能力画像摘要
- 匹配度
- 匹配依据
- 已满足条件
- 关键差距

### 8.3 招聘反馈

企业回填：

- 已查看
- 进入面试
- 已录用
- 拒绝
- 反馈原因

拒绝原因和面试反馈将回流学生端，由智能体转化为成长建议。

## 九、状态机设计

### 9.1 机会状态

```text
matched       系统已匹配，学生可查看
authorized    学生授权投递
ignored       学生暂不考虑
viewed        企业已查看
interviewed   进入面试
hired         企业录用
declined      企业拒绝
```

状态流转：

```text
matched
├── authorized → viewed → interviewed → hired
│                              └──────→ declined
├── ignored
└── declined
```

### 9.2 诊断状态

```text
draft             已建立档案，资料不足
pending_answers   等待学生回答追问
ready             可以开始诊断
completed         已完成诊断
needs_refresh     新证据或反馈导致结果待更新
```

### 9.3 任务状态

```text
pending       待开始
in_progress   进行中
submitted     已提交证据
verified      已核验
adjusted      已被新计划替代
```

## 十三、实施阶段

### S1：产品主线校正

目标：

- 删除学校人工推荐叙事。
- 将机会状态调整为 `matched → authorized → interviewed → hired / declined`。
- 学生端增加“职达机会”分类展示。
- 学校端导航压缩为治理后台。

验收标准：

- 学生可以自主授权系统匹配岗位。
- 学校不参与匹配和推荐流程。
- 企业只能看到已授权候选人。

### S2：职达首页

目标：

- 新增职达首页。
- 增加主目标、备选目标和每周时间预算。
- 展示本周任务、短板、机会和最近进展。

验收标准：

- 学生登录后无需理解多个报表即可知道下一步行动。

### S3：证据档案

目标：

- 新增 `student_evidence`。
- 为能力项增加证据来源和置信度。
- 支持项目链接和成长任务证据提交。

验收标准：

- 任意能力分数都可以解释其依据和可信程度。

### S4：智能体追问和工具调用

目标：

- 新增 `agent_questions` 和 `agent_runs`。
- 将 `ToolRegistry` 接入诊断流程。
- 支持资料不足时主动追问。
- 使用规则算法计算基础匹配分。

验收标准：

- 智能体能够根据资料完整度选择追问或继续诊断。
- 匹配结果可复算。
- 工具调用过程可记录。

### S5：滚动进阶路径

目标：

- 基于每周时间预算生成 1–3 个任务。
- 任务关联差距、资源、证据和完成标准。
- 新证据提交后局部刷新路径。

验收标准：

- 学生完成任务后，系统能解释计划是否调整以及为什么。

### S6：职达顾问

目标：

- 将职达顾问接入学生画像、计划、机会和反馈。
- 支持围绕当前状态提出具体建议。

验收标准：

- 职达顾问回答能够引用学生自己的数据，而不是给出通用建议。

### S7：学校后台和企业端接入真实 API

目标：

- 学校端完成学生管理、企业岗位治理和反馈记录。
- 企业端完成 JD 解析、岗位维护和反馈回填。
- 移除演示框架数据。

验收标准：

- 三端使用同一套真实数据完成闭环。

## 十四、非目标

本阶段明确不做：

- 完整教务系统
- 排课和选课系统
- 复杂课程体系诊断
- 培养方案自动迭代
- 学校人工人才推荐
- 复杂招聘 ATS
- 多级审批流
- 由 LLM 直接决定全部评分

这些能力只有在真实用户反馈证明必要时才进入后续规划。

## 十六、最终产品体验

学生感受到的产品不应该是：

```text
上传简历 → 查看一组图表 → 阅读一份报告
```

而应该是：

```text
系统理解我的现状
→ 指出还缺少哪些关键证据
→ 帮我比较现实可行的职业方向
→ 告诉我本周最值得做什么
→ 根据我的进展和企业反馈持续调整
→ 在合适时机提醒我自主投递机会
```

企业提供真实需求，学校维护可信环境，智能体承担持续决策支持。三方协同最终服务于学生获得更清晰、更可信、更可执行的成长路径。
